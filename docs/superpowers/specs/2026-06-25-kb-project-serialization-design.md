## 1. 目标与非目标

### 目标
1. 让 `serialize_project` 在**真实数据**上产出干净、以项目主题（技术领域/研究内容）为主导的自然语言文本，消除 `成果类型：X，成果名称：` 套话堆砌。
2. **捞回当前被静默丢弃的 5 个切断项目**（含高速公路改扩建、沉管隧道等最有分量的项目）及其 23 行成果续片。
3. 集中改在单一文件 `app/kbmap/project_serializer.py`，让入库（`chunker._chunk_jsonl`）与验证（`kbmap.embed`）共享同一改进，不分叉。

### 非目标
- **不改入库流水线编排**（`pipeline.py` 仍 `--kb X --dir Y`，`--manifest` 模式不在本设计范围）。
- **不端到端联调** Milvus / 不做召回评测（本轮为模板/清洗驱动，非评测驱动；评测留作后续）。
- **不动其他 5 个 KB** 的序列化（它们走结构感知 chunker，与本设计无关）。
- 不改 kb_project 在 6 库中的分类归属（验证报告显示其类间分离度 0.55–0.58，最优，无需调整）。

## 2. 现状与问题（真实数据量化）

当前 `_chunk_jsonl`（`app/ingest/chunker.py`）逐行 `startswith("{")` → `json.loads`；`serialize_project`（`app/kbmap/project_serializer.py`）只处理 9 个字段、正文以 `字段：值；` 拼接。在真实 230 个项目上量化出三类问题：

| 问题 | 数据 | 后果 |
|------|------|------|
| 🔴 成果套话是头号噪声 | `成果类型：X，成果名称：` 出现 **1671 次**（论文 576 / 专利 549 / 技术成果 172 / 著作 151 / 标准规范 92…） | 每条 `实际产出成果` 是几十~上百条套话堆砌，**淹没**项目主题；同项目内成果大量重复 |
| 🔴 长记录被导出器切断 | 5 条 JSON 未闭合（4300–4900 字符，溢出导出器切块上限），+ **23 行游离续片** | 5 个大项目整条丢失、续片静默丢弃 |
| 🟡 低价值/噪声字段 | 225 条全带 电话/邮箱/联系人/经费/决算 等 | 模板正文混入对语义检索无用的字段 |
| 🟡 正文半结构化堆砌 | `主要研究内容：…；预期成果指标：…；实际产出成果：…` 以 `；` 连成一串 + `预期成果指标` 含 `(项)\t\t,;` 垃圾 | 可读性差、字段名稀释 embedding 信号 |

## 3. 架构：三层纯函数管线（单一定义源）

`serialize_project` / `iter_jsonl_chunks` 同时被入库 `chunker._chunk_jsonl` 与验证 `kbmap.embed.extract_file_text` 调用。**改进集中在这一个文件**，两处自动受益。

```
原始文件文本
  │
  ▼  ① parse_projects(text) → list[dict]        【新增：容错解析】
  │     按 chunk_idx 标记切单元 → 剥 --- 分隔符
  │     → 容错字段提取（正则，不靠 json.loads）
  │     → 切断单元 + 紧随续片回接成一个逻辑项目
  │     → 输出 230 个 dict（225 完整 + 5 切断恢复）
  │
  ▼  ② clean_project(d) → d                      【新增：清洗】
  │     实际产出成果：剥套话 → 去重 → 平铺（去重全留）
  │     预期成果指标：清 "(项)\t\t,;" 垃圾
  │
  ▼  ③ serialize_project(d) → str                【改写：自然语言散文】
  │     字段取舍 + 头部散文 + 正文分句
  ▼
embedding 输入文本
```

全链路无随机 → **确定性 + 重灌幂等不变**（`segment_id = sha256(doc_id|ordinal|text[:64])[:16]`）。

## 4. ① 容错解析 `parse_projects`

### 为什么不用 `json.loads`
5 个切断项目的 JSON 未闭合（`实际产出成果` 字段值中途截断，无结尾 `}`，且丢失 `项目总决算`/`委外…决算费用` 等尾字段）。续片以字面 `\n` 开头，朴素"拼接 + 补 `}`"恢复 0/5（字面换行破坏 JSON 字符串）。

### 算法
1. 用 `re.split(r"(<!--\s*chunk_idx=\d+[^>]*-->)", text)` 切成 `(标记, 正文)` 单元序列。
2. 每个单元正文剥掉 `---` 分隔行 + 首尾空白。
3. 分类：`{` 开头且 `}` 结尾 = 完整；`{` 开头不闭合 = 切断；否则 = 续片。
4. **回接**：每个切断单元 + 紧随其后的连续续片拼成一个逻辑项目（实测 5 个切断分别带 8/7/3/3/2 个续片 = 23）。
5. **容错字段提取**：对每个逻辑项目文本跑 `"([^"\\]+)":"([^"]*)"` 逐字段匹配 → 建 dict。
   - 成果名 / 研究内容 / 经费值里**不含 `"`**，`[^"]*` 能干净吃掉整段值（含字面换行）。
   - 切断项目丢失的尾字段（决算/经费）自然缺失——**本就在字段取舍的丢弃清单里，无损**。

### 已知限制
若某字段值含转义 `\"`，正则会截断该字段尾部。实测 0 例；兜底：该字段取部分值或跳过，不影响其它字段。换 embedding 模型不触发此问题（与模型无关）。

### 接口
```python
def parse_projects(raw_text: str) -> list[dict]:
    """容错解析 kb_project 文件。返回每个逻辑项目一个 dict（字段名→值）。
    完整项目 + 切断项目（带续片回接）均返回。"""
```

> 兼容：`iter_jsonl_chunks(path)` 改为 `return [serialize_project(clean_project(d)) for d in parse_projects(read(path))]`，对外签名与返回顺序不变（按文件顺序），下游 `chunker`/`embed` 无需改。

## 5. ② 清洗 `clean_project`

### 5.1 `实际产出成果`：去重全留（用户已定）
- 剥套话：正则 `成果类型：(.+?)，成果名称：(.+?)\s*；` 提取 `(类型, 名称)`。
- **去重**：按名称去重（保序、首次出现；同项目内重复名常见，如"一种用于新泽西护栏的自动播种装置"出现 3 次）。
- **全留**：保留全部唯一名，平铺以 `；` 连接（用户选择，优先具体名召回，不压缩为计数）。
- 产出形如：`一种自锁式行走轮；索夹螺杆轴力的应变反演方法；…`
- 兜底：无 `成果类型：` 模式时，原样返回去空白后的文本。

### 5.2 `预期成果指标`：清垃圾
- 去 `(项)\t\t,;`、多余制表符/逗号/分号、连续空白。
- 清后若为空或仅余计数噪声则视为空字段（序列化时跳过）。

### 5.3 字段取舍（默认提案，spec 评审可调）
- ✅ 留：`技术领域`、`项目名称`、`项目编号`、`立项年份`、`承担单位`、`项目负责人`、`业务类别`、`主要研究内容`、`拟解决的关键技术问题`、`实际产出成果`（清洗后）
- ❌ 弃：`项目负责人电话/电子邮箱`、`项目联系人/电话/电子邮箱`、`依托工程`、`立项单位`、`申请单位`、`项目级别`、`项目开始/完成时间`、`项目预算总经费`、`委外外部研究开发预算费用`、`立项申请时间`、`合作单位`、`承担、参与单位工作及经费分配情况`、`项目概况`、`创新点`、`经济和社会效益评估`、`其它需要说明的问题`、`预期成果指标`（清后冗余/噪声）、`主要技术经济指标/项目考核指标`、`项目总决算`、`委外外部研究开发决算费用`

> 弃用字段不被删除（dict 保留全字段），仅 `serialize_project` 不输出。切断项目缺失的尾字段（决算/经费）本就在弃用清单 → 无损。

## 6. ③ 序列化 `serialize_project`（改写）

### 6.1 输出结构
1. **头部（一句散文，无字段标签）**：
   `{技术领域}领域的科研项目《{项目名称}》（编号 {项目编号}，{业务类别}），{立项年份}年立项，由{承担单位}承担，项目负责人{项目负责人}。`
   （`业务类别` 置于编号括号内；为空则括号内只留编号。所有字段值**原样输出**，不做改写/概括，保证确定性。）
2. **主要研究内容**（若有）：`主要研究内容：{主要研究内容}。`
3. **拟解决的关键技术问题**（若有）：`拟解决的关键技术问题：{拟解决的关键技术问题}。`
4. **已产出成果**（若有）：`已产出成果：{清洗后去重成果，；连接}。`

- 顺序遵循"主题在前"：技术领域 → 名称 → 元信息 → 研究内容 → 成果。
- 跳过空字段；空字段不产生分句。
- 顺序固定、无随机 → 确定性。

### 6.2 before / after（真实项目 JT2019YB15）
**前**（套话×11 含重复，联系人/经费/`(项)` 噪声混入）：
> `2019年立项的【桥梁工程】类项目《大跨径悬索桥缆索系统…研究》（编号 JT2019YB15），由广东省公路建设有限公司承担，项目负责人熊锋。主要研究内容：…；预期成果指标：1项专利授权发明专利(项)\t\t,;\n…；实际产出成果：成果类型：专利，成果名称：一种自锁式行走轮 ；…（套话×11）`

**后**（头部散文 + 成果去重全留 8 条；`主要研究内容` 原样输出，仅以 … 表示截断）：
> `桥梁工程领域的科研项目《大跨径悬索桥缆索系统全寿命周期腐蚀与防护关键技术研究》（编号 JT2019YB15，运营项目类），2019 年立项，由广东省公路建设有限公司承担，项目负责人熊锋。主要研究内容：我省自虎门大桥开始，建设了珠江黄埔大桥、虎门二桥等大跨径缆索承重桥梁…形成包括缆索系统检测技术、系统评估方法、腐蚀机理和控制技术以及养护规则的整套技术研究成果。已产出成果：一种自锁式行走轮；索夹螺杆轴力的应变反演方法；悬索桥主缆检修平台；桥梁缆索检测用检查车及其使用方法；行走装置及主缆检修平台；一种圆截面多层片材型CFRP拉索体系；基于能耗优化和无线通信的桥梁除湿微机控制系统；智能环境监测系统中无线传感器网络与物联网的集成。`

## 7. 集成点（接口不变）

| 调用方 | 当前用法 | 改动 |
|--------|----------|------|
| `app/ingest/chunker.py::_chunk_jsonl` | 逐行 `json.loads` → `serialize_project(obj)` | 改为 `parse_projects` + `clean_project` + `serialize_project`；`ordinal` 仍按文件顺序递增（确定性 segment_id 不变语义） |
| `app/kbmap/embed.py::extract_file_text` | `iter_jsonl_chunks(full)` 取首条 | `iter_jsonl_chunks` 内部升级，签名不变；首条现在是项目 1 清洗后文本（更干净的代表向量） |
| `app/kbmap/__main__.py` CLI | 不直接调 | 无改动 |

> `iter_jsonl_chunks(path) -> list[str]` 的对外契约（返回每项目一段序列化文本、按文件顺序）保持不变，仅内部实现升级。

## 9. 开放问题与已知限制

| 项 | 决定 | 备注 |
|----|------|------|
| 成果表示 | **去重全留**（用户定） | 优先具体名召回；大项目（如高速公路改扩建 ~50 唯一名）chunk 仍偏长，用户已知并接受 |
| 字段取舍清单 | 默认提案（§5.3） | spec 评审可调（如想保留 `创新点`/`主要技术经济指标`） |
| 切断项目尾字段丢失 | 接受 | 丢失的是决算/经费，本就弃用 |
| 容错正则遇转义 `\"` | 截断该字段尾部 | 实测 0 例；兜底跳过 |
| 评测 | 不在本轮 | 模板驱动；评测驱动留作后续 |
